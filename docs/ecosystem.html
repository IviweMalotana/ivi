How I work · one operator, AI projects

From your voice note to a shipped feature. Every step in one page.

You send me an idea. A few days later a working feature is live and you have a one-line release note in your inbox that reads back to your original ask. This page shows exactly what happens between. Every ticket lives in Jira. Every step names the agent that runs it and the artefact it drops on the ticket.

Jira Software · one project per stream · every step below writes back to the ticket

The flow

Idea in. Feature out. One trail through Jira the whole way.

Read top to bottom. The blue circles are agents doing the work. The dark circles are you (or me) at a human gate.

1 You

You send the idea. Any format.

A voice note in Slack. A rambling email. A whiteboard photo. You are not paid to write clean specs, so I do not need one from you.

What lands with me: whatever you actually sent. Text, audio, image.
2 Agent

The intake agent captures the idea into a working note.

Transcribes voice notes, OCRs the photo, pulls the shape of the request into a scratch document with three sections: what you want, why, and the questions I need to ask before I can write a ticket.

intake · sonnet 5.5
Artefact: a scratch note in Notion, linked to the eventual Jira epic. Not yet a ticket.
3 Agent

The ticket-writer agent drafts the Jira ticket.

Turns the intake note into a proper Jira story: summary, description, acceptance criteria as Given/When/Then, points estimate, blocking/linked issues. Assigns to me, leaves the status in Refinement so nothing starts until you approve.

ticket-writer · opus 4.7
Story AIP-142 Refinement

Cite every generated line back to a source document

ReporterYou
AssigneeIvi Malotana
PriorityP1 · Founder-flagged
Story points5
SprintSprint 12
Description. Reviewers can't defend an uncited claim to a client. Every generated sentence needs to trace to a real source paragraph, and un-sourced sentences should be visible for review (not silently dropped).
  • REQ-1 · Every generated sentence carries a source_id.
  • REQ-2 · Low-confidence sentences are quarantined to a "for review" tray.
  • REQ-3 · A reviewer can accept, reject or rewrite in one click; logged.
  • REQ-4 · Send is hard-blocked at citation-count = 0.
4 You
Human gate · validation

You validate the ticket. Right here, in Jira.

You get one link. You read four bullets. You reply with "yes", or you edit them. REQ-1 was per-paragraph in the draft. You wanted per-sentence. You said so. The ticket-writer agent picks up your comment, rewrites, and re-asks.

What you spend: two to five minutes. The ticket does not leave Refinement until you sign it off.
5 Agent

The spec-writer agent turns the approved ticket into a .feature file.

Cucumber BDD, plain Gherkin. One Scenario per requirement, tagged with the REQ. This file is the contract: it is what a human signs, and what cucumber-js runs on every PR. The spec and the test are the same document.

spec-writer · opus 4.7
@AIP-142 @founder-flagged Feature: Cite every generated line back to a source @req-1 @must Scenario: Every generated sentence carries a source_id Given the generated proposal contains N sentences When I open the proposal in the reviewer Then every sentence has at least one source_id attached And hovering the sentence reveals the citation card @req-4 @send-gate Scenario: Send is hard-blocked at citation-count = 0 Given a proposal about to be sent to a client When any sentence in the proposal has zero citations Then the Send button is disabled And a human-readable reason is shown
6 You
Human gate · sign-off

You sign off the Gherkin. This is the contract.

The status on the Jira ticket moves to Signed off. Automation fires. Nothing gets built or tested against anything except these scenarios.

Cost of a wrong sign-off here: low. Every requirement is one sentence. If you missed something, you catch it in five minutes rather than five days.
7 Agent

The test-planner agent generates the test plan from the Gherkin.

Reads the .feature file. Writes cucumber-js step definitions (one per Given/When/Then), Playwright page-objects for the flows, Vitest units for the small invariants, and a regression pull from last quarter's bugs. Attaches the plan to the ticket.

test-planner · opus 4.7
Artefact on the ticket: a test plan naming every file it will add, keyed to REQ-1..N. A requirement without a testable path fails this step loudly, not silently.
8 Agent

The builder agent writes the code.

Creates the feature branch, scaffolds the slice, writes one commit per plan-step. Refuses to touch files not on the plan. Opens a draft PR linked back to the Jira ticket so the human trail stays intact.

builder · sonnet 5.5
Artefact: a draft PR against your repo, branch feat/AIP-142-cite-every-line, commits keyed to REQ. Ticket status auto-moves to In Dev.
9 Agent

The test-runner agent runs every suite.

Cucumber + Playwright for the flows a user touches. Vitest for the small units. Regression for last quarter's bugs so we can prove they stayed dead. A red test names the failing scenario, its tag, and its REQ. Silent flakes cannot happen.

test-runner · haiku 4.5
Artefact: a pass/fail table posted as a Jira comment. Ticket moves to Testing. Green everywhere means the reviewer wakes up.
10 Agent

The reviewer agent runs an adversarial audit.

Different model to the builder, so they don't share blind spots. Reads the diff against the plan and the .feature file. Asks: what would make this break in staging? Posts findings as PR comments. Blocks merge on anything with a real failure scenario.

reviewer · opus 4.7
11 Agent

The release-writer agent drafts the release note.

Assembles the release note from the scenarios diff on the ticket, not the commit messages. The note reads as behaviour changes: what the software started doing, in plain English, one line per requirement.

release-writer · sonnet 5.5
Artefact: a one-page release note, attached to the ticket and queued for the Friday digest.
12 You
Human gate · verify

You verify on staging. Ticket closes.

You click the staging link. You try to break the feature. If it holds, you close the ticket. What ships to production is what you signed the Gherkin for. No release-note surprises.

Time from your voice note to this point: typically five to ten working days for a five-point story.

The agent roster

Six agents. Fixed model each. Cheap runs the loop, expensive runs the review.

Every agent is a Claude Code subagent with a scoped tool set. Model ids are fixed in the subagent front-matter, so the cheap one cannot silently escalate itself.
